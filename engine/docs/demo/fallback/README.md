# Fallback media

> **Superseded for the final presentation (2026-09-24).** This document
> describes the earlier six-minute demo, which erased the USB stick live on
> stage. The final presentation is the 4.5-minute order in
> [`docs/validation/demo-evidence-index.md`](../../validation/demo-evidence-index.md),
> answered from [`docs/validation/judge-defense-card.md`](../../validation/judge-defense-card.md).
> It performs **no** physical write: the Sanitize beat stops at the approval
> gate and erase is not pressed. Keep this file for its measured numbers and
> fallback commands. Do not rehearse from its timings.

Nothing in this directory is generated by `demo-reset.sh`. It has to be recorded
by hand, once, and re-recorded whenever the UI changes shape. **Record it during
a rehearsal that went well** — a fallback captured while fixing something is a
fallback that shows the thing being fixed.

`docs/demo/runbook.md` names each of these by path. If a file here is missing,
that beat has no fallback and the runbook's "if it fails" row is a lie.

## Which of these the run currently staging can produce

`--full` writes the artefacts. It does **not** write a single capture — every
`.png` and `.mp4` here needs a person at the keyboard with a recorder running.

**Available the moment staging finishes, no extra session:**

- `demo-erase.forensic.json` and `demo-ledger/` — the two `cp` commands above.
  Do this first; it is the only fallback that protects the strongest beat.
- Every staged JSON the 1:30 and 2:15 command fallbacks read. Already on disk.

**Needs a separate capture session, with the server up and the browser open:**

- `devices.png` — needs the UI and the tooltip open.
- `recovery.png` — needs a completed carve on screen with a candidate selected.
- `wipe-start.mp4` — **needs a real wipe to start**, which means 50 seconds of a
  destructive run. Capture it during a rehearsal you were going to run anyway;
  do not start a wipe solely to film it.

Because `wipe-start.mp4` costs a wipe, capture it during **rehearsal 1**, not
before it: the first rehearsal already begins with a live wipe at 0:45, and
recording that one costs nothing extra.

## Verify the report fallback still works

Run this after copying it, and again before every rehearsal:

```bash
SANCTUM_KEY_PASSPHRASE=sanctum-demo .venv/bin/python -m core.report.cli \
    verify-report docs/demo/fallback/demo-erase.forensic.json \
    --ledger-root docs/demo/fallback/demo-ledger
```

Five `[PASS]` lines and `Result: PASS`, then `Verdict: VERIFIED_WITH_LIMITATIONS`
with one reason per declared limitation or residual-risk finding, then a `Note:`
line about identity that always prints. Each `[PASS]` is followed by a *sentence*, not a status word —
`chain_integrity` reads "N excerpt entries hash correctly and all N-2 adjacent
pair(s) link …", not `VERIFIED_PARTIAL`. If `chain_store` or
`fingerprint_matches_genesis` reads anything other than a success sentence, the
ledger copy and the report are from different resets and the fallback is
useless.

## What is deliberately not here

**No pre-recorded PhotoRec scan and no pre-recorded carve.** Both beats already
read their numbers from JSON files that `demo-reset.sh` writes, and the runbook's
fallback for both is the hardware validation run in
`docs/validation/results-20260905T033655Z/`, which is real measured data rather
than a recording of a screen.

**Nothing is committed.** These files are large, and the report and ledger carry
a signing key's fingerprint from a scratch state directory. `.gitignore` covers
them; this README is the only tracked file in here.
